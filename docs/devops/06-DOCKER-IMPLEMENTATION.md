# Docker implementation and validation

Production Dockerfiles reuse the staging entrypoint, trust bundle, Chromium renderer, shared contracts and build commands. All FROM lines and infrastructure images are pinned to registry-resolved immutable digests; exact references are in `deploy/config/base-images.json`. Node images build all workspaces/Prisma clients and prune development dependencies for runtime. A separate migration target retains migration tooling. PDF adds Chromium/fonts and preserves its sandbox requirement. Python uses a dependency stage with existing pinned constraints, strips pytest requirements from runtime installation, and copies service code without test suites. Frontends build separately with relative public URLs and run nginx as a non-root user.

Application runtimes run as node/runtime/nginx users. ENTRYPOINT exec preserves signals, Compose init reaps children, and bounded graceful-stop periods are configured. Health checks use verified internal TLS; readiness and rendering are separate deployment gates. Credentials are never build arguments or image files. The Docker ignore file excludes local secrets, env, key/state/runtime artifacts.

Executed locally: root + hybrid-overlay Compose parse/merge; production Compose parse and full interpolation with newly generated synthetic credentials; network/port/secret/resource assertions; actual Caddy v2.11.7 validation with a disposable CA; production setup/config generation in an ignored private directory. The Caddy download was SHA512-verified. No HTTP listener or production ACME request was started for that check.

Blocked: every Docker image build, final application image filesystem/layer scan, startup/health scheduling, private-network packet tests, memory/PID enforcement, volume ownership/restart behavior and actual container rollback. The host Docker CLI reports no daemon socket. CI builds and scans all six distinct image targets; publishing covers all 13 named images (12 applications plus migration). Do not describe configured CI jobs as executed GitHub runs.

Chromium sandbox startup failed in the development sandbox despite liveness being healthy. A separately launched diagnostic renderer produced a real PDF with a test-only unsandboxed launcher; this is not production sandbox validation. Validate the production host/kernel/seccomp/user-namespace combination and actual signed PDF generation before enablement. Do not solve this by globally disabling the browser sandbox.

Exact disposable staging commands and Docker requirements are in the setup guide and hybrid report 15. Compose must support env_file format raw (v2.30+); use a current supported Engine/Compose release. [Docker Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/) documents per-service secret mounts and residual privilege considerations.

Remote scans can run without a Docker daemon: Trivy scanned pinned Caddy/nginx/Node/Python/PostgreSQL/Redis images and found release-blocking advisories, including critical findings in several Debian bases. Exact counts/advisories and the bounded Ollama scan status are in evidence/base-image-scans.json and dependency-security.json. Final application layers are still unbuilt/unscanned. Blocking CI scans reject every HIGH/CRITICAL finding by default; no blanket unfixed-advisory suppression is configured.
