# Environment and secrets audit

Names and source locations were audited before production implementation. [configuration-inventory.json](configuration-inventory.json) contains 294 discovered names, classifications, owners and source paths. Values were never copied into this inventory. New deployment controls are separately enumerated in the production schema and example.

Classification totals: BUILD-TIME CONFIGURATION: 2, INTERNAL CONFIGURATION: 254, PUBLIC CONFIGURATION: 6, SENSITIVE CONFIGURATION: 32. Build-time public URLs use VITE_API_BASE_URL=/v1 and VITE_ADMIN_API_BASE_URL=/api/v1. Firebase web configuration is an existing public client identifier, not a backend credential. Auth verifies Firebase tokens server-side. Restrict its authorized domains/API usage in the owning Firebase project.

Gitleaks 8.30.1 scanned all two available Git commits and current source/private local artifacts. The 273 historical matches were 258 SHA256 integrity hashes, nine framework-description prose matches, five isolated synthetic fixture values, and one public Firebase identifier. No committed backend provider secret was confirmed. See [secret-scan-redacted.json](secret-scan-redacted.json), which contains names/locations/classifications only. Initial private working-tree scanning also matched six credential assignments in five ignored service env files and 23 entries in an ignored Redis dump. Provider validity was not checked; no external credentials were used, rotated or revoked.

Preventive scanning now passes using narrow hash/prose/public/synthetic exceptions. Private env files and the local Redis dump are excluded from the preventive directory scan, while a separate Git boundary check rejects these artifacts even if force-added. Historical scanning used the full default detector rules before exceptions. No history was rewritten. Existing private development credentials remain operator-owned and must not be copied to production. Rotate any credential known to have been disclosed elsewhere; this scan does not establish external account validity.

Docker build contexts exclude env files, private keys, local execution state, deployment secrets/runtime files and Terraform state. Production Docker builds accept only the frontend APP selector; no production credentials are build arguments. Compiled admin/user assets passed backend-secret/private-key/connection-string pattern checks. Actual image-layer scans/builds remain blocked locally without Docker and are mandatory in CI/staging.

Environment injection remains necessary for existing DB/Redis/JWT/provider loaders. Those values are visible to the owning process and Docker administrators. File-based identities/TLS/AI keyring are isolated per service, read-only. Docker/root access is therefore privileged and is withheld from the SSH deployment identity.
